Focus: making the council feel like it's *processing* what the user says,
not just transcribing. And starting to chip away at three sidebar/UX

## Shipped

### 1. Structured restatement of interim Q&A — "Here's what the council heard" panel

The old "what the council heard" section just echoed the question and the
user's raw answer verbatim. It always felt like a transcript, never like
the council was processing. Now every submitted interim answer triggers a
single Gemini Flash call (~$0.0001, ~2s) that returns:

  - **2–5 bullets** restating the answer in second person, breaking
    composite replies into discrete beats.
  - **Tagged entities** (people / places / dates / numbers / orgs /
    works) rendered as color-tinted chips so users can see at a glance
    what the model picked up.
  - **0–2 inferred implications**, clearly hedged with reasoning prefixes
    ("Likely:", "Suggests:", "Reads like:") so the system never feels
    like it's putting words in the user's mouth.
  - **Related prior facts** — up to 3 hits from `user_fact` ranked by
    entity-phrase substring match + token overlap with the new answer.
    Rendered under "Building on what you've told us before" so the
    cross-essay memory is finally *visible*.

All four sections are gated on data presence, so a thin answer that
yields no inferred lines simply skips that block.

**Loading state**: between submit and the Flash call landing, the panel
shows "Listening — the council is organizing what you just said…" with
a pulsing gold dot. Users never see a dead echo gap.

**Failure mode**: any error returns empty lists and the UI falls back to
the verbatim answer. The panel never crashes; the worst case is "no
upgrade."

## In flight (started today, not yet shipped)

### 2. Sidebar topic visibility + topic name during generation

The user pointed out two sidebar problems:
  - Conversation titles show truncated `TOPIC: Personal Statement AU…`
    because the "title" was literally `first_50_chars(user_message)`.
    "TOPIC: " ate 7 chars of visible width before the actual subject.
  - Until the title finally landed (end of stage 3), the sidebar showed
    nothing meaningful for the entire 60–90s drafting flow.

**Backend (started)**: `backend/council.py` —
  - New `heuristic_conversation_title()` strips the `TOPIC:` / `DRAFT:`
    prefix, drops everything after the first newline (so AUDIENCE / KEY
    IDEA scaffolding doesn't leak in), trims to ≤60 chars.
  - `generate_conversation_title()` now uses one Gemini Flash call to
    polish the heuristic into a 3–6-word Title Case label. Falls back to
    the heuristic on any failure so the sidebar is never titleless.

**Still pending**: frontend sidebar (`Sidebar.jsx`, `Sidebar.css`) to
strip any residual prefix at render time, allow 2-line wrap, show audience
as a sublabel, and surface a pulsing dot for actively-streaming convos.
Plus App.jsx wiring to (a) set an optimistic title from the topic line at
conversation-create time so the sidebar has a name within milliseconds,
and (b) move the early `title_complete` emission so the polished title
arrives ~2s in instead of at run-end.

### 3. Parallel streaming sessions

Currently, starting essay B while essay A is mid-draft aborts A (one
global `AbortController` in App.jsx). The plan is to switch to a
`Map<conversationId, AbortController>` and a `Set<conversationId>` of
currently-streaming conversations, so switching the active conversation
just swaps which one the UI shows — both keep streaming. Soft-cap at
~3 concurrent drafts to keep rate-limit cost predictable.

Backend already supports this (each `/message/stream` request is
independent); this is a frontend refactor.
