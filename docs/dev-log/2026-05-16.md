## Shipped

### 1. Structured restatement of interim Q&A — "Here's what the council heard" panel

The old "what the council heard" section just echoed the question and the
user's raw answer verbatim. It always felt like a transcript, never like
the council was processing. Now every submitted interim answer triggers a
single Gemini Flash call (~$0.0001, ~2s) that returns:

  - **2–5 bullets** restating the answer in second person, breaking
    composite replies into discrete beats.
  - **Tagged entities** (people / places / dates / numbers / orgs /
    works) rendered as color-tinted chips so users can see at a glance
    what the model picked up.
  - **0–2 inferred implications**, clearly hedged with reasoning prefixes
    ("Likely:", "Suggests:", "Reads like:") so the system never feels
    like it's putting words in the user's mouth.
  - **Related prior facts** — up to 3 hits from `user_fact` ranked by
    entity-phrase substring match + token overlap with the new answer.
    Rendered under "Building on what you've told us before" so the
    cross-essay memory is finally *visible*.

All four sections are gated on data presence, so a thin answer that
yields no inferred lines simply skips that block.

**Loading state**: between submit and the Flash call landing, the panel
shows "Listening — the council is organizing what you just said…" with
a pulsing gold dot. Users never see a dead echo gap.

**Failure mode**: any error returns empty lists and the UI falls back to
the verbatim answer. The panel never crashes; the worst case is "no
upgrade."

Files:
  - `backend/intake_expansion.py` (new module — Flash prompt + parser +
    related-fact ranker)
  - `backend/main.py` — `POST /api/intake/expand` endpoint
  - `frontend/src/api.js` — `api.intake.expand` wrapper
  - `frontend/src/App.jsx` — fire after each answer, attach
    `{expanding, expansion}` to the question entry
  - `frontend/src/components/InterimQuestions.jsx` — new `HeardItem`

### 2. Sidebar topic visibility + topic name during generation

Two sidebar problems the user flagged:
  - Conversation titles showed truncated `TOPIC: Personal Statement AU…`
    because the "title" was literally `first_50_chars(user_message)`.
    The `TOPIC:` prefix ate 7 chars of visible width before the actual
    subject was even visible.
  - Until the title finally landed (end of stage 3), the sidebar showed
    nothing meaningful for the entire 60–90s drafting flow.

Fixes:
  - **`backend/council.py`** — new `heuristic_conversation_title()`
    strips the `TOPIC:` / `DRAFT:` prefix, drops everything after the
    first newline (so AUDIENCE / KEY IDEA scaffolding doesn't leak in),
    trims to ≤60 chars. `generate_conversation_title()` now makes one
    Gemini Flash call to polish the heuristic into a 3–6-word Title Case
    label (~$0.0001, ~1–2s). Falls back to the heuristic on any failure
    so the sidebar is never titleless.
  - **`backend/main.py`** — opportunistic `title_complete` flush after
    `pitch_picked` fires. If `title_task.done()` is true (almost always
    by then), we persist and emit the polished title immediately, so the
    sidebar upgrades from heuristic → polished within ~5–8s of Send.
    The end-of-run await remains as a fallback.
  - **`frontend/src/App.jsx`** — `deriveTitleFromMessage()` mirrors the
    backend heuristic so the sidebar gets an optimistic title within
    milliseconds (no round trip needed). The `title_complete` event now
    patches the title in place via setState instead of full-reloading
    the conversation list — cheaper and no flicker.
  - **`frontend/src/components/Sidebar.jsx`** — `cleanTitle()` helper
    strips any residual prefix at render time, so OLD conversations
    created before the polish lands also read cleanly without a
    migration. Empty/null titles render as "Drafting…" when streaming,
    "New Conversation" otherwise.
  - **`frontend/src/components/Sidebar.css`** — 2-line clamp on
    `.conversation-title-text` (was `nowrap` + ellipsis). Pulsing gold
    dot on `.conversation-streaming-dot` for active streams.

### 3. Parallel streaming sessions

Old model: one global `abortControllerRef` + `requestIdRef` boolean
`isLoading` — starting a new essay while one was mid-draft yanked the
controller out from under the old run, but more importantly, the SSE
events for the new stream would land in `setCurrentConversation` calls
that targeted whatever conversation the user was now looking at,
corrupting it.

New model:
  - **`abortControllersRef`** is now a `Map<convId, AbortController>` —
    each `handleSendMessage` call installs its controller under the
    target conversation id and never touches other entries.
  - **`streamingIds: Set<convId>`** state replaces the boolean
    `isLoading`. `isLoading` is now a derived value
    (`streamingIds.has(activeConvId)`).
  - **`safeSetConv`** is a stream-local setter that wraps the outer
    `setCurrentConversation` with a guard: if the visible conversation
    is no longer the target of THIS stream, the update is a no-op. All
    26 `setCurrentConversation` call sites inside `handleSendMessage`
    were swapped to `safeSetConv` so background streams can't corrupt
    the active view.
  - **`handleAbort(convId?)`** now takes an optional conversation id so
    each conversation's "Stop" button stops that specific stream. The
    sidebar's existing Stop button passes the current id (unchanged
    UX for single-stream users).
  - **`useEffect` on `currentConversationId`** now skips
    `loadConversation()` if the conversation has an active stream —
    avoids clobbering in-memory state with the empty/stale server
    payload mid-flight.
  - **Sidebar** receives `streamingIds` and renders a pulsing gold dot
    per streaming conversation; the css landed in #2 above.

Known limitation (acceptable for v1): when the user navigates away from
a streaming conversation, live progress for that conversation is not
retained in memory. The stream still runs to completion server-side and
the final essay loads on next visit. Surfacing live progress for
background streams would require a per-conversation in-memory cache;
flagged as the obvious next step in the commit message.

## Notes for next session

- Test the heard-panel expansion in production — specifically watch for:
  - Inferred lines that feel presumptuous (would tighten the prompt)
  - Related-facts that pull in noise (would raise the score threshold
    from ≥2 to ≥3)
  - Latency spikes if the Flash call slows down (consider a 5s budget
    with a `wait_for` timeout and "expansion: null" fallback)
- Live progress for background streams: cache `currentConversation`
  state in a `Map<convId, conversation>` ref so switching back into a
  streaming conversation shows the partial state from the active stream
  instead of reloading empty/stale data from the server.
- Title generation is now one extra Flash call per essay run — cheap, but
  add a metric to confirm latency is actually ~1–2s in practice. If it's
  slower, the heuristic alone is already a big win and the polish becomes
  optional.
